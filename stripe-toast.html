STRIPE + TOAST

How we get inside the network that already moves the money.

Toast owns the floor and, crucially, processes the payment itself. Stripe owns the only shipping agent-payment tooling. Between them they are the shortest path from an agent that plans a night to an agent that can actually pay for one. This is what exists today, what doesn't, and the order to attack it in.

01 — THE MECHANICS

How a restaurant actually processes a payment.

Worth being precise about, because every integration argument below turns on where in this chain a third party can insert itself. The critical detail: Toast is not just the POS. It is the payment facilitator too — the processing margin is a large part of why Toast exists, which is exactly why it guards the position.

02 — WHAT IS ACTUALLY AVAILABLE

Verified, as of August 2026.

Sourced from primary developer documentation. Where something could not be confirmed it is marked as such rather than assumed.

VERIFIED Toast has no reservation API

Toast's own integration documentation states there is no reservation API. A separate availability service covers online-order capacity, not table slots. A reservation is modelled as a placeholder Order — a workaround available only to certified reservation-system partners.

VERIFIED Toast has a real partner program

Public docs at doc.toasttab.com and a partner program running since 2016. Application and certification gated, not self-serve, but genuinely open to apply — unlike Resy, which has no public application path at all.

VERIFIED Toast Orders API returns the outcome

Available to certified partners that a restaurant has explicitly authorised. This is the half of the loop nobody else can give us: what the table actually ordered and spent. No explicit no-show field found.

VERIFIED Stripe ships the agent payment tooling

Agentic Commerce Suite (Dec 2025) and Issuing for agents (Apr 2026) — virtual cards scoped to an agent with spend controls. The most mature agent-payment product available today, with real developer docs rather than a waitlist.

VERIFIED Autonomous spend does not exist yet

Stripe's own documentation states every agent transaction currently requires human review before the credential is shared. Nobody has shipped unattended agent spend — so design the product around confirmation, not autonomy.

VERIFIED Amex owns the reservation side

Amex owns Resy and Tock, and announced a multi-year partnership with Toast in Aug 2025 to feed guestbook data into Toast and launch a consumer booking surface. The reservation layer is consolidating into a competitor.

04 — PLAN OF ATTACK

The order to do it in.

Every comparable company — Resy, Tock, SevenRooms — started with direct, manual, single-city restaurant relationships and reached network-level partnership years later, unlocked by capital or acquisition rather than by a developer application. Plan for that shape.

0–6 MONTHSNo platform API. Direct restaurants, concierge fulfilment.
  • Hand-picked list in one city. Relationships signed restaurant by restaurant, the way Resy and Tock both started.
  • Booking happens through the restaurant's existing consumer flow or a human in the loop. This is not an integration and must never be described as one.
  • Cars and tickets via deep links and affiliate paths — both confirmed to need zero approval.
  • Apply to Toast's partner program now anyway. It is application-gated, and the queue is the point.
6–18 MONTHSCertified Toast partner. Stripe carries the money.
  • Toast Orders API through certification, per restaurant authorisation. That gets the outcome half of the loop — covers, spend, dwell.
  • Stripe Agentic Commerce Suite plus Issuing for agents as the payment instrument, with a scoped credential per guest rather than one card fronting the table.
  • Human approval stays in the flow. Stripe's own docs still require it, so build the UX around confirming rather than around autonomy.
  • Volume becomes the argument. Nothing else opens a reservation network.
18–36 MONTHSReservation access, or the acquisition conversation.
  • Earliest plausible window for a Resy/OpenTable-calibre deal, based on precedent (2.5–6.5 years, and always unlocked by capital or acquisition).
  • Amex owns Resy and Tock and is partnered with Toast. Assume that path opens only through an equity event, not a developer application.
  • OpenTable and SevenRooms are the realistic gated-but-open alternatives; Square is self-serve but has no restaurant reservation product at all.
  • By here the graph should be the asset being bought, not the booking flow.
05 — THE AGENTIC ARGUMENT

What we bring that they can't build alone.

LEVERAGE We arrive as demand, not as software

Toast sells software to restaurants. We arrive with a party of four, a time, and a card already attached. That is the one thing an operator always wants more of, and it is a fundamentally different conversation from another vendor asking for API access.

LEVERAGE We hold the sequence they can't see

Toast sees one table. Stripe sees one charge. Neither sees that the table happened because of a show two hours later and a person who recommended it. That sequence is the asset, and it is only assembled at our layer.

LEVERAGE Payments is where the value settles

Because Toast processes as well as records, an agent that reliably drives pre-committed, pre-split parties is driving processing volume — the thing Toast actually monetises. Frame every conversation in covers and processed volume, never in features.

RISK They can build the consumer surface

Local by Toast plus Resy and Tock guestbook data is exactly the discovery surface we would compete with. Assume the platform sees this. The defence is the graph and the provenance chain, not the booking flow.

THE ONE-LINE VERSION

Apply to Toast now and build the direct-restaurant business as though the API will never arrive. Use Stripe as the money layer from day one, because it is the only part of this that actually ships today. Treat reservation access as an outcome of traction, never as a prerequisite for it.
